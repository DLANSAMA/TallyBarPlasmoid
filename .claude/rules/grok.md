# Grok Build and Grok Bot

Area contracts moved out of the root CLAUDE.md; they load only when a matching file is touched.

**Grok is a live bar with a local-log fallback — weekly credit bar from the billing endpoint or `unified.jsonl`, token/cost history from the log only.**
- **Live read:** with the network allowed, `run_grok_local(network=True)` asks `_BILLING_URL` (`https://cli-chat-proxy.grok.com/v1/billing?format=credits`, one GET per refresh) with `Authorization: Bearer <token>`, where the token is the `key` of the latest-expiring record in `~/.grok/auth.json` that is still more than `_TOKEN_EXPIRY_MARGIN_SECONDS` (60) from its `expires_at` (`_grok_access_token`; a record with no parseable `expires_at` or an empty `key` is skipped). It is **never refreshed and `refresh_token` is never read** — only the CLI renews the sign-in, so the live read works until the access token lapses and the log covers the rest. The reply's `config` is shaped like a log event and goes through the same `parse_grok_billing_config` (`_live_billing_event`). The request gets `max(1.0, min(8.0, timeout / 2))` seconds of WALL clock — `_call_within` runs it on a daemon thread and abandons it at the budget, because urllib's timeout bounds each socket operation, not the whole request or DNS; without that a stall outlasts the provider timeout and the log reading is lost with it (Grok is not carried forward). The `_run_grok` closure in `build_snapshot` passes `network=not args.no_network`; `run_grok_local` defaults to `network=False`, so `--no-network` and every caller that doesn't opt in read the log only. **Any failure** (no usable token, a network error or stall, non-200, an unreadable body, a `config` that doesn't parse, a period end that is unreadable or already past) silently returns the log reading. A reply without a percent obeys `_latest_billing_event`'s rule: it is 0% only when its period starts after the log reading's explicit-percent one, else the log reading wins; nothing from the request (token, response body, exception text) reaches a message or diagnostic.
- **Source and tier:** a live reading carries `source: grok-billing-api` and `fetchedAt` = the fetch time (so it is never `stale`); a log reading carries `source: local-grok-build` and the event's own timestamp. The endpoint omits the plan name, so the live reading's `tier` is taken from the log reading's event (`_latest_billing_event`) when there is one and is absent otherwise.
- **Log reading (the fallback, and the whole story under `--no-network`):** `run_grok_local` (providers/grok.py) reads the newest usable `billing: fetched credits config` event from `~/.grok/logs/unified.jsonl` → the weekly credit-pool bar (xAI's own `creditUsagePercent`), tier, and billing period (`parsers.parse_grok_billing_config`). The event is logged at session start, so a long session buries it far from EOF — the chunked reverse scan (`_iter_billing_events_reverse`) is load-bearing; don't replace it with a fixed "last N KB" window. An event without `creditUsagePercent` means 0% only when it opens a NEW period; mid-period it is skipped in favour of the last real reading (`_latest_billing_event`).
- **A log reading's freshness is the CLI's, not ours:** `fetchedAt` is the event's own timestamp, and a reading older than `_BILLING_STALE_AFTER_SECONDS` sets `stale` (the UI's "(cached)" suffix). Don't stamp `now_iso()` on a log reading.
- **An ENDED period rolls forward** (`roll_period_forward`): the newest billing event can describe a period that's already over (the CLI only logs while it runs). `run_grok_local` then shows 0% with the reset projected to the current weekly period (`period.projected`), and `grok_billing_period` returns the current window (non-weekly ended ⇒ None). Both take `now=` — tests with past periods must pin it.
- There is no context-window gauge on the Grok tab — it was removed deliberately; don't reintroduce one.
- **History:** `local_grok_token_summary` parses `unified.jsonl` lines `msg=="shell.turn.inference_done"` (OpenAI-shaped `ctx`: `prompt_tokens` INCLUDES `cached_prompt_tokens`, `completion_tokens` INCLUDES `reasoning_tokens` — don't add reasoning). The usage line carries no model: `_parse_grok_file` tracks it from the log's model-change lines (`model_by_sid` — the per-line state that bars it from incremental parsing), and the summarizer fills remaining gaps out-of-band from `sessions/**/summary.json` (`_load_grok_session_models`, default `grok-build`) — NOT in the parser, which must stay a pure function of the log's bytes. `grok_billing_period` feeds the summary's billing-week window (`billingWeekTokens`/`billingWeekCost`).
- **A day held by both the log and the archive takes the larger figure** (tokens and cost from ONE source) for the today/7d/30d totals, bars and model breakdown; `merge_grok_archive` keeps the live record when it is at least as large, so the summary treats any other archived day as the winner. The hourly bars stay live (the archive has no hours). `billingWeekTokens`/`billingWeekCost` replace a whole local day inside the billing week with its archived figure; the day the week starts or ends in is a partial day and keeps the log's records. → `tests/test_grok_archive.py::test_a_partly_rotated_day_*`, `::test_the_billing_week_line_*`.
- `unified.jsonl` rotates, so per-day totals are mirrored into `~/.tallybar/grok_archive.json` (`merge_grok_archive`: a day only ever grows, 120 days kept, change-gated, `.bak` mirror).
- The CLI's `grok-build`/`grok-composer` models are subscription-proxied and absent from LiteLLM → priced at xAI's published coding-model API rate via the embedded `pricing_data` rows ("Cost (if pay-per-use)"). `grok-4.6` needs its own exact key or family matching resolves it to `grok-4`.
→ `tests/test_providers.py::test_run_grok_local_*`, `::test_grok_*`, `::test_grok_live_*`, `tests/test_backend.py::test_grok_asks_the_live_endpoint_*`, `::test_grok_reads_only_its_log_*`, `tests/test_accounting.py::test_local_grok_*`, `tests/test_parsers.py::test_parse_grok_billing_config_weekly_credits`.

**All Grok usage (Grok, Grok Build, Grok Bot) draws on ONE limit, so there is ONE Grok tab and no `grokbot` provider in the snapshot.** `build_snapshot` still runs `providers/grok_bot.run_grok_bot` (an `api_task`: `--no-network` never schedules it) as an internal reading, carries it forward like claude/gemini/codex off the previous snapshot's `grok.grokBotReading`, and `providers.grok.fold_grok_bot` merges it into the Grok provider. The pool bar is ALWAYS the billing endpoint's (or its log's) `creditUsagePercent` — Grok Bot's own percent differs by fractions of a point and never overrides a current one. The one exception: when the Grok reading is `stale` (the CLI's sign-in lapsed, only an old log line is left) and Grok Bot's `fetchedAt` is newer, Grok Bot's Weekly row, `source`, `fetchedAt` and plan name replace the Grok ones (the `period` and the cost figures stay Grok's), because an hours-old pool number is further off than that fraction; the bar's split by product is `productUsage` (`parsers.grok_product_split`, shown as the Weekly row's `sublabel`, dropped when an ended period rolls to 0%). Grok Bot adds only the On-demand row, the prepaid line and a plan name Grok lacks; its failure never touches a Grok reading. With no Grok CLI reading it stands in for the bar, and a failure with a remedy (locked wallet, expired sign-in) is shown on the Grok tab. A saved `grokbot` tab setting keeps Grok enabled (`_enabled_providers`). → `tests/test_providers.py::test_fold_grok_bot_*`, `tests/test_backend.py::test_grok_bot_*`, `::test_public_config_keeps_grok_on_for_a_saved_grok_bot_tab`.

The Grok Bot reading itself shares nothing with `run_grok_local`: no `~/.grok` logs, no Grok archive, no cost scan, no cost card.
- **Bearer:** the account's `cursor-access-token` in `~/.config/Grok Bot/sand-secrets.json` (`active` account, else the only one; `cursor-accounts` is plain JSON). Values are `plaintext:v1:<b64>`, `scoped:v1:<64 hex>:<b64>`, or a base64 Chromium `v10`/`v11` blob, decrypted with `cookies.decrypt_chromium_value(family="chromium")` and the Chromium Safe Storage password from the provider's OWN `KWalletClient(background=…)`, opened only when a value is encrypted and closed straight after. Its `wallet-locked`/`wallet-state-unknown` is the provider's status, never relabelled through the gemini/claude cookie loop. Never refreshed; the refresh token and profile (email) are never read. No store or no signed-in account is `not-running`; a value that won't decrypt, or a 401, is `unauthorized`.
- **Secrets never reach output:** the token, machine id, account scope and checksum are never interpolated into a message or diagnostic. Error messages are fixed strings plus the HTTP status and the validated Connect `code`, never a response body or `str(exc)`. `http_text` refuses redirects for any request carrying `Authorization` (`_RefuseRedirects`): urllib's default handler copies the bearer onto the redirect target, `http://` included. → `tests/test_http_helpers.py::test_refuse_redirects_*`.
- **Weekly bar** = `GetSandUsageStatus.usagePercent`, already a percent (clamped 0–100, never ×100). Pooled team allowance or no finite percent → `ok` with no bar, never an invented 0%. **On-demand row** only when `hasNonZeroIncludedLimit` is true, both `spendLimitUsage` cent fields are numbers, and `0 < individualLimit < 2147483647` (int32 max is the app's "unlimited"). Label `On-demand` puts it in the existing extra-usage slot.
- **Plan name:** `grokPlanLabel` unless it is a generic label (`_GENERIC_PLAN_LABELS`: "Grok Bot plan"), then `cursorPlanName`, then "Grok"; a Grok-brand name gets " week". An X subscription arrives as its own label ("Premium"). → `tests/test_providers.py::test_grok_bot_x_subscription_plan_name`
- **Prepaid line:** for a unified account with time left, one `GetUserPrepaidBilling` POST; only a `…_PREPAID` billing mode (last `_` token — `POSTPAID` contains "PREPAID") with `spentThisMonthCents` (an int64 string) above 0 sets `extraUsageText`. The endpoint carries no balance. Any failure keeps the weekly bar. → `tests/test_providers.py::test_grok_bot_prepaid_*`
- `SAND_CLIENT_VERSION` and the header set track the app's own requests; re-verify the headers and checksum against its asar when bumping it.
- **`x-cursor-checksum` follows the app's JavaScript (`Tg`/`kut`), not Python intuition:** JS `>>` is int32 with a five-bit shift count, so `t>>40`/`t>>32` are `t>>8`/`t`. Python's real 40/32-bit shifts zero the first two bytes and produce a checksum the app never sends.
→ `tests/test_providers.py::test_grok_bot_*`, `tests/test_backend.py::test_grok_bot_*`.
